# 变更控制 Skill

## 何时使用

在本仓库（`demo_web`）内进行任何代码、配置、样式、测试或文档修改时，必须先使用本 Skill。

## 不可违反的规则

1. **先锁范围，再改代码**
   - 用一句话写清本次需求。
   - 列出允许修改的文件和代码块。
   - 列出明确不动的文件。
   - 需求没有提到的代码，不改、不重构、不格式化、不排序、不重命名、不删注释、不调空格。

2. **一次修改一份记录**
   - 每次修改都在 `docs/changes/` 下新增一份 Markdown 记录。
   - 命名：`YYYY-MM-DD-<短横线英文或拼音slug>.md`。
   - 同一天同一需求只建一份；追加内容时保留原记录。
   - 记录先写“计划改动”，修改完成后补“实际改动”和“验证结果”。

3. **最小 diff**
   - 能改一行就只改一行。
   - 能加一个属性就不替换整段。
   - 不顺手修 typo、不顺手统一引号、不顺手调整缩进。
   - 不允许因为编辑器保存导致整文件换行符或空白变化。

4. **隐藏与删除分开**
   - 需求说“隐藏”，优先用 `v-show="false"`、`v-if="false"` 或显式开关，不删除原功能代码。
   - 需求说“删除”，才移除代码，并在记录中说明不可恢复点。

5. **提交前检查**
   - `git diff --check`：不能有空白错误。
   - `git diff --stat`：只能出现记录中列出的文件。
   - `git diff`：逐段确认没有需求外的改动。
   - 运行相关测试；涉及页面的至少跑 `pnpm test:demo`。
   - 如果测试因本次需求必须调整，测试改动也要写进记录。

## 标准流程

1. 阅读需求，确认目标文件和现有实现。
2. 在 `docs/changes/` 新建记录，填写：
   - 日期、分支、基线提交
   - 需求原文
   - 允许修改的文件与代码位置
   - 明确不动的范围
   - 计划改动
3. 只改需求相关代码。
4. 运行类型检查和测试。
5. 补全记录：
   - 实际 diff（文件、行号、增删行数）
   - 验证命令与结果
   - 未改动确认
   - 回滚方法
6. 最后再跑一次 `git diff --check` 和 `git diff --stat`。

## 失败处理

- 如果发现工作区已有需求外改动，先停下来，不要继续叠加修改。
- 只回滚需求外的 hunk，不整文件 checkout，避免误删本次需求改动。
- 如果无法在不改其他代码的前提下完成需求，先在记录中写明冲突点，再等确认。
