## 数据库载体与类型

项目目前没有后端及既定数据库，因此本轮不擅自指定生产数据库或搭建服务。SQLite 用于在本机实际建表、导入 fixture、验证关系和约束。此 SQL 不能直接宣称是 MySQL/PostgreSQL 的生产迁移；确定后端后需转换布尔、时间、JSON、索引语法并补并发锁与迁移机制。

| 数据 | 约定 |
| --- | --- |
| 内部主键 | `id TEXT`；现有 mock 为兼容沿用业务编号，正式导入时可分开生成 |
| 单据编号 | `document_no` 独立唯一；旧系统编号保留，不重新编码 |
| 日期 / 时间 | 业务日期 `YYYY-MM-DD`；事件时间 UTC ISO 8601。新 mock 业务日期以 Asia/Shanghai 当天生成，历史期初流水保持原日期 |
| 数量 | 整数；单据数量大于 0；库存余额允许负数；无单位换算 |
| 单价 | `*_micro`，百万分之一元的整数；展示和计算时按已确认业务精度处理 |
| 金额 | `*_cents`，人民币分；未知金额用 NULL，不以物料参考价填采购价 |
| 税率 | `tax_rate_bp`，基点；1300 表示 13% |
| 空值 | 未提供的审核人、日期、成本、价格均保持 NULL，不能用假人名或当前时间补历史记录 |

金额字段在正式接口中宜用十进制字符串传输，避免大整数越过 JavaScript 安全整数范围。当前前端算法仍按原有“两位小数单价乘数量”执行，本轮不悄悄升级精度。

## 分表与关系

主档是仓库、物料、商品分类和会计分类。分类保留父子关系，会计分类独立；完整编码清单待业务提供，不虚构三级树。客户用自由文本，供应商保留单据文本快照，不新增未授权的客户或供应商管理页。

工单关联多个计划；计划物料是独立快照，`quantity_basis` 区分单台用量与总需求，导入来源直接落计划和计划行，`import_rows_json` 保留原始多行合并的导入记录。无独立 BOM 主档及 BOM 版本表，不恢复已取消的 BOM 维护需求。手工计划亦固化物料行，避免以后修改示例产品 BOM 改写既有计划。

底稿与请购各有头、行；采购行最多关联一种需求来源，也允许手工行无来源。同品号多来源保留多行；采购按源行 ID 追溯，需求量不可因采购执行而覆写。已采购量、剩余量通过有效采购行汇总，不能另维护一个易漂移的计数。已合并原采购单排除执行与汇总。正式后端合并时为新采购行生成新 ID，`merged_from_line_id` 指向原行，需求来源保持原关联；当前前端合并沿用行 ID，本轮不改其行为，不能直接将这类运行态对象当成 SQL 行插入。

收货头关联采购单，收货行关联采购行。`receipt_lines.quantity` 表示安排数量，`actual_quantity` 表示实收；两者分开保存，避免确认差额后丢失原始安排。待收占用由未生效收货行汇总，实际到货由已生效实收汇总。采购行的 `received_quantity` 仅作事务内更新的查询缓存，不接受客户端直接写入，必须与实收汇总一致。参考结构允许超收，但当前前端仍保留不超收校验。

入库凭证和库存流水分开；其他入库没有采购来源，采购入库一对一关联收货单。领料行关联计划物料及领用仓库；现场仓与领用仓是不同角色，不能合并。成品入库独立关联工单；整单发货与工单一对一，成品出库凭证与发货一对一。出库凭证仅记录执行，不二次扣库存。

分析批次、分析结果、采购修改版本、打印模板、模板版本、打印记录、操作日志合计 7 张表是后续能力预留，本轮不假称已接入 UI 或已有历史记录。

## 审核、执行状态与计算值

审核与执行分开：`audit_status` 仅未审核/已审核；计划执行、采购收货进度、工单阶段使用各自字段。为兼容现有演示，计划状态同时容纳当前“已领料”与文档“已备料”，最终含义需另行确认，不能直接互换。

审核人和时间只有真实审核动作发生时填写。参考 SQL 默认“未审核”仅表示初始状态，不意味着本轮已为请购、发货实现审核。历史已审核计划可以审核人为空，并在页面后续展示为“历史信息未提供”。

以下是查询/视图结果，不建重复真值表：库存仓库矩阵、工单统计、到货趋势、需求已采购/剩余量、领料累计、计划缺料汇总、物料名称关联展示。单据合计汇总行金额；库存金额不是现有参考价乘现存量，成本来源未实现时显示未知。

单据物料名称、规格、单位可存行级快照，避免主档改名改变历史合同；基础演示尚只依赖主档，本轮不改变历史展示语义。单据抬头的币种、汇率、供应商名称为快照；多币种结算与本币金额暂不实现。

## 一致性与错误处理

1. 审核生效、库存余额、流水、来源累计查询和凭证创建必须在同一个数据库事务内完成。正式后端需要行锁或带 revision 的条件更新，并检查影响行数；当前本地前端仍由 store 的副本提交保障原子保存。
2. 同源行、同方向库存流水唯一，入库收货引用唯一，发货及成品出库引用唯一，避免重复生效。
3. 外键默认 RESTRICT/NO ACTION，不使用级联删除业务历史；停用与删除分开，有引用不能物理删除。反审核应生成可追溯冲销或执行明确回退，不能抹去原审核记录。
4. 跨类型来源（三元组）、采购来源物料一致、收货采购行归属、领料计划行归属、整单发货数量及可用仓规则由服务在同一事务内校验，不能仅依赖页面。SQL 外键只约束存在性，不等于这些业务约束均已实现。
5. 行金额/税额在服务端按统一舍入规则计算；不接受客户端任意填写派生金额。版本快照、打印模板版本、日志追加后保持不可变，生产接口不得提供普通编辑入口。
6. 首次基线库存为权威期初余额，继承的两条旧流水不是完整历史账。不能用这两条流水重算全部库存；未来迁移应登记独立期初凭证并从切换时点核对增减。

## 文档差异的本轮处理

| 分歧 | 本轮处理 |
| --- | --- |
| 允许负库存 vs 当前库存不足拦截 | 结构允许负数；前端规则不改 |
| 允许超收 vs 当前剩余应收限制 | 不增加数据库超收上限；前端规则不改 |
| 请购、发货需要审核 | 表结构预留，mock 不冒充已完成审核；当前流程不改 |
| 计划“已备料”与当前“已领料” | 结构兼容，页面暂不改名，不用累计领料推定齐料 |
| 文档计划完工后发货 vs 第二轮工单足量入库后发货 | 保留第二轮已实施行为，独立成品入库表保留 |
| 需求源取数永不递减 vs 文档建议默认剩余预填 | 保留完整源需求量取数，已采购/剩余作为未来展示信息 |
| Q008 支持部分发货 vs Q091 本期不做 | 采用文档 12.1 澄清：部分领料、超收可设计，发货整单 |
| 邮编、换算分子分母、结束代码、BOM 版本 | 不新增这些字段；历史对象中的邮编不自动删除 |
| 批次、序列号、多币种、会计分类、委外 | 标注待定或延期，不以推测填业务值，不启用计算 |

文档头部“91 条已确认/4 条待解释”与末章已闭环表述不一致；Q011/Q012/Q020/Q023 仍为待定，不把“全部闭环”理解成完整清单已提供。原文中的建议也不自动变成已授权业务改动。

## mock 接入与兼容

`model.seed()` 现在调用 `createMockState()`，实际应用首次打开及重置都从 `mock/database.json` 的关系表初始化。固定示例产品 BOM 仍用于新增业务，已有计划改为独立行快照。原导入的真实物料目录继续从 `product-materials.json` 追加，保留原字段及来源说明，不复制一份维护；因此基础关系 fixture 只有 7 个演示物料，并不声称包含完整导入库。

原有浏览器缓存仍使用 `wsn-erp-demo-v1`，不覆盖用户已保存单据。已有数据不会因本轮重组而被重置；新增基础 mock 需在新浏览器环境或由用户主动重置后加载。本轮不会自动执行重置。

关系表字段命名使用 snake_case，当前页面模型保留 camelCase，适配只发生在 mock 初始化边界，不把数据库表名扩散到 Vue 页面。本轮适配仅接受基线支持的表；尚未支持的业务表若非空会明确报错，不静默丢单。数据库预留字段不等于当前 State 已包含全部字段。

`createMockScenarios()` 返回四套相互隔离的 State：基础待办、分批到料、领料与成品入库、整单发货。后三者调用现有业务函数生成，不手填库存与状态。它们供后续页面开发和验证导入使用，本轮不添加场景切换按钮，也不替换用户本地数据。

## 验证方式

仓库根目录执行 `python web/docs/database/verify_schema.py`：在内存 SQLite 实际创建全部表、导入基础关系数据，并验证外键、唯一性、非法数量、金额、税率及重复流水。前端运行 `mock-data.test.ts` 和原有演示回归，核对缺料数量、来源行、场景库存及历史数据兼容；类型检查与构建沿用项目工具链。
